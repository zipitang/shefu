# 《摄伏》开发文档

本文件面向接手这个项目的开发者 / 你自己三个月后。
它回答三件事：**规则层怎么组织的**、**数据怎么生成的**、**改东西改哪里**。

## 一、分层架构

```
┌─────────────────────────────────────────────────────────┐
│  UI 层  scripts/ui/*.gd                                  │
│  HallScreen   BattleScreen   CodexScreen   CardView      │
│  只负责「把状态画出来」+「把点击翻译成引擎调用」           │
└───────────────────────┬─────────────────────────────────┘
                        │  调用公开方法 + 监听信号
┌───────────────────────▼─────────────────────────────────┐
│  规则层  scripts/core/GameState.gd  （★ 唯一真相源）       │
│  回合流程 · 资源结算 · 道具 · 拔除 · 克制判定 · 胜负       │
│  ── 零 UI 依赖，可以在 --headless 下完整跑完一整局 ──      │
└───────┬───────────────────────────────┬─────────────────┘
        │                               │
┌───────▼──────────┐         ┌──────────▼──────────────────┐
│ EffectRunner.gd  │         │ AIBrain.gd                  │
│ 把 effect 字典   │         │ 只产出「动作列表」，          │
│ 解释成状态变更    │         │ 由 UI 逐步播放（决策可见）    │
└───────┬──────────┘         └─────────────────────────────┘
        │
┌───────▼──────────────────────────────────────────────────┐
│  数据层  data/*.json  ← 由 tools/*.py 生成                │
│  cards.json  characters.json  mingli.json  rules.json     │
└──────────────────────────────────────────────────────────┘
```

**关键约束**：`scripts/core/` 里不允许出现任何 `Control` / `TextureRect` / 布局代码。
只要守住这条，规则就能被无头测试覆盖，也随时能搬到服务端做权威模拟。

## 二、一局对战的生命周期

```
Main.show_hall()                        # 大厅：只选角色 / 人数 / AI 难度
  ├─ 「开始匹配」→ show_battle(cfg)      # 一键直达，局内选【人】→命理
  └─ 「开房间」  → show_room(cfg)        # RoomScreen：房号 + 座位 + 开始对局
                       └─ start_game → show_battle(cfg)

BattleScreen.start_battle(cfg)
   ├─ _build()                          # 先搭界面骨架
   ├─ cfg.auto_setup ? _begin_game()    # 截图/测试模式：跳过开场选择
   └─ 否则 _show_setup(0)               # ① 选【人】大本营
        └─ 确定 → _show_setup(1)        # ② 选命理
             └─ 确定 → _begin_game(ren, mingli)
                  └─ GameState.setup(seats_data)
                  └─ BattleScreen._driver()          # 主循环（协程）
                        while not finished:
                           start_turn()              # false = 跳过死亡玩家
                           ├ 人类 → 解锁 UI，return，等玩家点「结束回合」再回到循环
                           └ AI   → AIBrain.plan_turn() 产出动作数组
                                   逐个 await 0.42s 播放（玩家能看清 AI 做什么）
                                   end_turn()
```

> 关键：**`GameState` 直到选完【人】与命理才创建**，所以开场选择层期间
> `battle.gs == null`（`UITest` 就是在断言这一点）。

`start_turn()` 内部固定做四件事：
1. 回合内标记复位（免费刷新 / 拜神 / 三选一 / 升级）
2. 场面冷却与状态递减（主动技能 CD、冻结、封锁）
3. `settle_wealth()`（财曲线 + 阵营特殊结算）
4. `open_draft()`（三选一牌面，本回合的经济窗口由此打开）

`end_turn()` 额外做两件事：清临时增益、**结算力竭**（`_apply_fatigue`，
第 `fatigueStartRound` 回合起每回合流失【气】），然后 `advance_cursor()` + `check_win()`。

之后玩家用右侧操作台依次执行第 3–10 步。**没有自动战斗阶段**。

### 三选一 = 常驻「取牌台」（点卡即取）

> ⚠️ 这一节描述的是**当前**模型。历史上它换过三版，下面「动作顺序铁律」保留的是
> 上一版留下的教训，读的时候请注意区分。

```gdscript
GameState.open_draft()        # 铺开 draftCount 张；**不再**在取牌后自动收摊
GameState.draft_take_cost(p)  # 本次取牌要花多少【财】（免费额度内返回 0）
GameState.can_take_draft(p)   # 轮到自己 + 付得起 + 没超付费上限
GameState.do_take_draft(i)    # 取走第 i 位，**立刻把这一位补成一张新牌**
GameState.close_draft()       # 收起牌面（玩家点「收起牌面」或 end_turn() 时）
```

| 规则 | 值 | 说明 |
|---|---|---|
| `draftCount` | 3 | 牌面张数 |
| `draftFreePerTurn` | 1 | 每回合免费取牌次数，**不扣【财】** |
| `buyCost` | 3 | 免费额度用完后每张的价钱 |
| `draftPaidCapPerTurn` | 3 | 每回合最多再**付费**取几张（防一回合买空牌面） |
| `refreshCostLadder` | `[1,2,3]` | 刷新阶梯，第一次免费 |

要点：

* **没有「取走 / 购买」按钮**，点卡面就是取牌（`_take_draft(i)`）。
* **取走的位置立刻补一张**（`do_take_draft()` 里 `CardDB.random_card()` 回填），
  所以「刷新」和「再取一张」永远有对象可用 —— 这正是旧版 `pick_draft()` 的病根：
  它会把 `current_draft` 整个清空，导致排在其后的刷新/购买**静默失败**。
* 取不走的位置在 UI 上整体压暗（`cell.modulate = Color(0.62, 0.60, 0.66)`）。
* 非凡人阵营（`is_mortal_faction() == false`，如法师）没有【财】，
  免费额度用尽后 `can_take_draft()` 直接返回 false。
* `pick_draft()` / `do_buy()` 作为薄包装保留，只为兼容 `SelfTest` / `BalanceTest` / 旧调用。

### 冷却：数值在核心层，视觉在 UI 层

冷却回合数**只由核心层负责**，UI 只读不写：

```gdscript
CCard.set_cooldown(n)   # 进冷却：cooldown = n，同时记下 cooldown_span = n
CCard.raise_cooldown(n) # 「至少 n 回合」，不缩短已有冷却（袭人 / 镇压用）
CCard.tick_cooldown()   # 自己回合开始时减 1；归零时把 span 一并清掉
```

`GameState.start_turn()` 里对 `p.board` 逐个 `u.tick_cooldown()`；
`GameState.do_active()` 里 `u.set_cooldown(maxi(1, u.active_cd()))`
（**下限 1**：数据里漏写 `cd` 也不能同回合反复发动）。

UI 端（`CardView`）：

* `cd_cur = card.cooldown`，`cd_max = maxi(cd_cur, card.cooldown_span)`。
  用 `span` 而不是 `active_cd()` 当分母，是因为「袭人」只上 1 回合冷却而技能 CD 是 3，
  用 `active_cd()` 当分母会导致刚用完只盖住 1/3 的卡面。
  兜底：`span` 丢了就退回 `active_cd()`，`cd_cur > cd_max` 时以 `cd_cur` 为准，分母永不为 0。
* `_draw_overlay()` 画黑幕：`cut = h * cd_cur / cd_max`，从 `y=0` 盖到 `y=cut`
  → **黑幕自下而上褪去**；下沿有 18 级"融化"渐变 + 一道冷光线 + 「⟳ N」。
* `_draw_glow()` 画冷却结束的四边外发光，**必须画在 `_glow_layer` 上**：
  它是 `_face` 的**兄弟**节点，因为 `_face.clip_contents = true` 会把所有溢出卡面的
  绘制裁掉（画在 `_overlay` 上就退化成贴着边的两条暗线）。
  光晕距离用**屏幕像素**不乘尺寸系数 —— 场面卡只有手牌一半大，
  按尺寸缩放的话发光只剩 3px，根本看不见。

### 动作顺序铁律（旧版遗留，`pick_draft()` 已不再清空牌面）

```gdscript
GameState.can_refresh(p) # if current_draft.is_empty(): return false
GameState.can_buy(p, i)  # if idx >= current_draft.size(): return false
```

这两个前置条件仍然存在，所以**只要牌面是空的，刷新与取牌就都做不了**。
旧版 `pick_draft()` 会 `current_draft = []`，于是唯一合法的顺序是：

```
升级【人】 → 刷新牌面 → 购买 → 取牌（免费）
（三者共用同一个【财】余额：避免先买光牌、再也升不起级）
```

现在 `do_take_draft()` **不再清空牌面**，所以这个顺序约束已经从"铁律"降级为"无害"；
但 `AIBrain.plan_turn()` 仍然保持「经济阶段在先」，因为它要留【财】给后续动作。

> 调试建议：`BalanceTest` 支持 `SF_DEBUG=1`，会逐条打印 AI 动作及其
> `ok=true/false`，这类"静默失败"一眼可见 —— 本轮就是靠它定位到本 bug 的。

### 手牌起乩的两条路径

```
① 拖拽：CardView._input 累积位移 > 12px → drag_started
          → BattleScreen._on_card_drag_start   生成跟随幽灵卡
          → _on_card_drag_move  → _drop_ok(gpos) 判定（落点在手牌区上方）
          → _on_card_drag_drop  → _play_card(c)
② 点击：点手牌 → 浮动操作条「起乩」按钮 → _play_card(c)
```

两条路径共用 `_play_card()`；拖拽用 `_suppress_click` 保证松手那一刻
不会把拖拽误判成一次点击。

## 三、技能系统：数据即逻辑

每张卡的技能都是**纯数据**，存在 `data/cards.json` 的 `skills` 字段：

```json
"skills": {
  "on_play":   { "name": "阴风侵体", "desc": "上场时对对方【人】造成 1 点气伤。",
                 "effects": [{ "type": "damage_qi", "target": "enemy_ren", "value": 1 }] },
  "on_remove": { "name": "怨魂反噬", "desc": "...", "effects": [...] },
  "passive":   { "name": "群鬼同悲", "desc": "...", "effects": [...] },
  "active":    { "name": "袭人", "cd": 1, "desc": "...", "effects": [...] }
}
```

`EffectRunner.run(gs, effect, actor, ctx)` 用一个大 `match` 解释这些 `type`。
目前已实现 40+ 种效果，命名规律：

| 前缀 / 关键字 | 含义 | 例 |
|---|---|---|
| `heal_qi` / `damage_qi` | 改【气】 | 目标 `self_ren` / `enemy_ren` |
| `draw` / `discard_enemy` / `discard_self` | 手牌增减 | |
| `gain_res` / `steal_res` | 财/法/源 增减 | `res`: `wealth`/`fa`/`yuan` |
| `damage_board` / `heal_board` / `damage_board_all` | 场上单位攻防 | `side`: `self`/`enemy` |
| `remove_unit` 系列：`destroy_di` `execute_board` `sacrifice_board` | 拔除 | 触发下场技能 |
| `freeze_board` / `seal_hand_card` / `fog_hand` | 控制 | 冻结 / 封印 / 隐藏手牌 |
| `buff_qi_damage` / `multiply_qi_damage` | 本回合气伤增幅 | 社火燃傩就是 ×2 |
| `aura_*` | 被动光环 | `aura_tian_hp` / `aura_wealth` … |

**加新效果 = 在 `EffectRunner` 的 match 里加一个分支**，不需要动 GameState。

### 3.0 技能从「按 sub 的四张表」改为「原型池 + 确定性取样」

**问题**：旧版 `tools/build_cards.py` 里 `on_play / on_remove / passive / active`
四个函数各自只有一张 `sub → 一条模板` 的字典（7 条 / 7 条 / 7 条 / 2 条）。
于是**技能完全由 sub 决定**，跟卡牌本身无关。实测 227 张卡里：

| 槽位 | 旧：不同技能名数 | 旧：最高频 | 新：不同技能名数 | 新：最高频 |
|---|---|---|---|---|
| `on_play` | 147（签名技能撑起来的） | 奉神降世 ×33 | **183** | 归墟献祭 ×4 |
| `on_remove` | **7** | 神威余烬 ×102 | **40** | 冰封遗恨 ×10 |
| `passive` | **7** | 天威压地 ×102 | **46** | 明王怒目 ×10 |
| `active` | **6** | **镇压 ×130**、袭人 ×85 | **51** | 搜魂 ×10、呼风 ×10 |

玩家反馈的「怎么所有人技能都是镇压什么的」就来自 `active()` 里那两个
`if sub in (...)` 分支：`神`+`佛`=132 张全走「镇压」，`妖/鬼/魔/奇兽`=87 张全走「袭人」。

**现在的做法**（`tools/build_cards.py`）：

1. 每个槽位一份大原型池 —— `ONPLAY_POOL` 42 条、`ONREMOVE_POOL` 36 条、
   `PASSIVE_POOL` 45 条、`ACTIVE_POOL` 51 条，另加道具专属的
   `ITEM_ONREMOVE_POOL` / `ITEM_PASSIVE_POOL`。
2. 取样键是**卡牌自己的 id**（`tian_佛_000` 这种），不是 sub：
   `start = zlib.crc32(f"{cid}|{slot}|{bump}") % n`，再向后游走取第一条
   「本分组还没用过」的原型。
3. 三条硬约束，全部由 `_pick_pool_entry()` 保证：
   - 全卡池内**四元组**（四个槽位的技能名）唯一 —— 实测 227/227；
   - 同一张卡四个槽位的技能名互不相同；
   - 同分组内尽量不撞名（36 张【齐名百圣】不会再共用同一招）。
4. `subs` 是**软偏好**（70% 从本阵营气质池起步），`factions` 是**硬约束**
   （`("天",)` 的光环只发给天阵营的卡，否则【地】卡顶着「己方【天】+1【祇】」是死被动）。
5. 主动技能额外按 `school`（攻/守/控/术/财）在 2 阶 / 3 阶追加一段效果，
   追加效果**刻意与自家基础效果不同类型的维度**（攻→抽牌、守→财、控→伤害…），
   并打上 `fixed: True` 以免叠加 `per_tier` 造成双重放大。

> **不能改用内置 `hash()`**：Python 每个进程都会给字符串哈希掺随机盐，
> 那样每跑一次生成器就会得到一份不同的卡牌数据，无法复现也无法 diff。

> **`rules.json` 是生成物**。手工只改 `data/rules.json` 会被下一次
> `tools/build_cards.py` 直接覆盖 —— 所有规则常量的唯一真源在脚本的 `RULES` 字典里。

### 3.1 技能数值随阶数成长（两种基准）

技能效果里的数值不是写死的，而是 `value + per_tier × k`，运行期由
`CCard._scaled_effects(key)` 展开。`k` 有两种取法：

| 基准 | `k` 的算法 | 谁在用 | 为什么 |
|---|---|---|---|
| **1 阶为基** | `k = tier - 1` | 原型池技能（不带 `fx` 的槽位） | 同一套原型挂在越高阶的卡上就越强 |
| **自身阶数为基** | `per_tier_from_base` → `k = tier - base_tier` | 签名技能（带 `fx` 的槽位） | 签名技能的描述里写的是**原阶数值**；同名卡只有一阶（图鉴即确定），描述文字永远准确 |

`tools/build_cards.py` 的 `_apply_tier_scaling()` 在生成末尾自动补 `per_tier`：
凡是 `SCALE_SAFE` 白名单内、带正整数 `value`、且尚未声明缩放的効果，都会按
`max(1, value // 3)` 得到步进；签名技能再打上 `per_tier_from_base`。
`aura_enemy_di_atk` 刻意不在白名单里 —— 它是「取最大值」的光环，必须恒定。
**带 `fixed: True` 的效果会被 `_apply_tier_scaling` 跳过** —— 主动技能在 2/3 阶
追加的那几段用它，避免「多拿一段效果」+「每段数值翻倍」的双重放大。

描述文字用 `{v0}` / `{c0}` / `{t0}` 占位符（下标 = 效果在 `effects` 数组里的位置），
由 `CCard.skill_desc()` 替换成展开后的真实数字。`SelfTest §9` 会校验
**没有任何未展开的占位符**漏到界面上。

> 签名技能的原阶数值 + `per_tier_from_base` 这套设计的关键前提是：
> **同名卡在卡池中只有一阶**（Round D 已实测确认 `同名多阶: 0`，合成功能随之移除）。
> 所以「原阶时的数值」永远等于描述里写的数字。

### 3.2 特效链路（fx）

```
CCard.fx_for_type(effect_type)        # 40+ 效果类型 → 25 种特效名
   ↑ 签名技能可在 skills.<slot>.fx 里显式指定
CCard.skill_fx(slot)
   ↓ EffectRunner.run() 统一广播
game_state.effect_fired{ kind:"skill_fx", fx, etype, pid, uid }
   ↓ BattleScreen._fx_effect
FXLayer.play_fx(fx, gpos, color, from)   # 符箓魔法阵 / 刀光 / 粒子 / 光环 / 震屏 / 闪光
Sfx.play_fx(fx)                          # 映射到 32 个合成音效之一
```

音效由 `tools/build_audio.py` 用**纯 Python**（`wave` + `struct`）合成，
`scripts/ui/Sfx.gd`（Autoload）负责播放：12 路 `AudioStreamPlayer` 对象池、
懒加载 + 缓存、缺失文件只警告一次、60ms 内同音压制 6dB、±6% 随机变调。

## 四、数值表（改平衡改这里）

```

刷新价阶梯 `refreshCostLadder: [1,2,3]`，购买价 `buyCost: 3`。

卡牌数值在 `tools/build_cards.py`：

def stats_for(top, sub, tier, is_special=False):
    天: hp = tier, atk = tier, atk_qi = 0     # 神佛不能伤人
    地: hp = tier, atk = tier, atk_qi = tier  # 地是刀
```

【祇】的动态上限在 `PlayerState.tian_base_hp()`：

```gdscript
tier + ren_count - 1 + aura_tian_hp()
```

即 **阶数 + 己方【人】数量 - 1**，与设计文档 7.2 完全一致。

### 4.0 上场限制：场位上限（随轮数）与同名牌唯一 `boardCap` / `boardUnique`

两条限制都由**规则层**统一裁决，UI 与 AI 走同一个入口，不允许各写一份：

```gdscript
GameState.board_cap(p)            # clamp(base + round_no * perRound, base, max)
GameState.play_block_reason(p, uid)  # → "" 表示可上场；否则返回**给玩家看的中文原因**
GameState.can_play(p, uid)        # == (play_block_reason == "")
```

`rules.json`：

| 键 | 值 | 含义 |
|---|---|---|
| `boardCap.enabled` | `true` | 是否启用场位上限 |
| `boardCap.base` / `perRound` / `max` | `2` / `1` / `7` | 第 0 轮 2 张，每轮 +1，封顶 7 张 |
| `boardUnique.enabled` | `true` | 同一张卡（同一 `id`，**跨阶数也算**）不能同时留在自己场上 |

四个容易被忽略的点：

1. **道具不占场位、也不受上限限制**（`play_block_reason` 对 `faction == "道具"` 直接放行）——
   道具是即时结算的消耗品，如果让它占位，手牌里的道具等于永久堵死一个场位。
2. **临时单位（三清铃的【僵尸】）也不占数额**。占用数用 `PlayerState.board_occupied()`
   （只数 `temp_turns <= 0` 的单位），不能用 `board.size()`。
3. **特殊技能可以多上几张**：`PlayerState.board_bonus` 累加到 `board_cap(p)` 上
   （如 万骨魔君/蝗神 的 on_play 带 `{"type": "board_bonus", "value": 1}`）。
4. **`AIBrain` 必须走同一个 `can_play`**。旧版 AI 自己按 `board.size() < 5` 判断，
   规则改成随轮数增长后它会一直计划一些永远执行不了的动作，表现为"AI 回合空转"。
5. **拦截原因要具体**。`play_block_reason()` 返回的字符串会被 `BattleScreen._show_toast()`
   直接弹给玩家：「场上已达上限（第 3 轮最多 5 张）…」/「场上已有同一张【二郎神】，不能重复上场」。
   统一回一句"无法起乩"会让人以为是自己点错了。

> **`rules.json` 是生成物**：这两条规则最早只写进了 `data/rules.json`，下一次跑
> `tools/build_cards.py` 就被整个覆盖掉，规则层读到的是空字典 ——
> 表现是"同名牌能重复上场、场位也没有上限"。**唯一真源在脚本的 `RULES` 字典里。**

### 4.0.1 多人局战区布局（Round E 重构）

敌方区不再是「一行大本营 + 一行混排的敌方场面卡」，而是**按座位对称分列**：

- 3 人局 → 2 列（左上 / 右上）；4 人局 → 3 列（左上 / 正中 / 右上）。
- 每列 = `VBoxContainer[ 大本营头部, HFlowContainer(该玩家的场面卡) ]`，
  列与列 `SIZE_EXPAND_FILL` 均分宽度 → 天然对称，每位玩家的上场区被隐形划分。
- **卡多自动换行**：HFlowContainer 超过列宽换到下一行（4 人局敌卡缩小到
  `BOARD_W×0.84`，7 常规 + 3 僵尸也只要两行）。

两条**回归红线**（都真实踩过）：

1. **场面行绝不能用 `ScrollContainer`（AUTO 横向滚动）**：卡一多滚动条出现，
   内容从「居中」跳到「左对齐 + 可拖动」，整个画面左移跳动 —— 即用户报的
   「多人局打到后面画面左移」bug。
2. **绝不能用 `CenterContainer` 包 `HFlowContainer`**：CenterContainer 把子控件压到
   **最小尺寸**，而 Flow 的最小宽度 = 一张卡（132px）→ 整列卡竖着堆成 2152px 高
   溢出屏幕。要横向居中用 `FlowContainer.ALIGNMENT_CENTER`（逐行居中）。

【辟邪】铜钱剑特效图（`assets/ui/fx_ward.webp`，由 `build_ui_assets.py` 的
`dump_wide()` 从 `道具/铜钱剑特效图/辟邪.png` 生成，横向素材必须保比裁剪）：
生效期间横于**己方**人卡上方 / **对手**人卡下方，作为人卡 `TextureRect` 的浮动子节点
挂载 —— 不占布局空间，层数归零即隐藏，不会顶动整排大本营。

### 4.1 主动行动额度 `actionsPerTurn`

回合流程里「主动技能」是**一个步骤**，不是「每张场上卡各打一次」。
一开始按字面实现成「所有场上卡都能攻击」，结果单局从 22 回合缩到 **8 回合**、
先手胜率飙到 90%（`scripts/BalanceTest.gd` 复现）。

现在 `rules.json` 里的 `actionsPerTurn: 2` 表示：每回合可消耗 2 次主动行动，
**袭人与场上主动技能共享这个额度**。额度消耗点只有两处（都在 `GameState`）：

```gdscript
do_attack()  →  p.actions_used += 1     # 校验在 can_attack() 开头
do_active()  →  p.actions_used += 1
```

额度在 `PlayerState.reset_turn_flags()` 里随回合重置。

扫参结果（`BalanceTest.gd --actions`，2/3/4 人局各 40 局）：

| 额度 | 平均回合 | 2 人局先手胜率 | 3 人局偏斜 | 4 人局偏斜 |
|---|---|---|---|---|
| 1 | 24.1 | 72.5% | 22.5 | 32.5 |
| **2** | **22.4** | **65.0%** | **25.0** | **15.0** |
| 不限 | 12.6 | 90.0% | 30.0 | 23.3 |

### 4.2 2 人局后手补偿 `duelCompensation`

先手在抢三选一 / 抢【财】/ 抢上场上都早一步，这个领先会滚雪球。
以下为 **2026-10 修好 AI 经济 bug（见 #18）后的重测数据**，每组 300 局、配对种子：

| 后手补偿（气:财） | 平均回合 | 先手胜率 |
|---|---|---|
| 0:0 | 11.1 | **72.1%** |
| 0:10 | 11.4 | 70.4% |
| 0:20 | 11.0 | 70.8% |
| 0:40 | 10.9 | 70.0% |
| 10:2（旧值，已废弃） | 14.7 | 64.2% |
| 22:2 | 17.2 | 51.0% |
| 23:2（当时采用，现已废弃 → 见 §4.2.2 取 `10:2`） | 17.3 | 49.7% |
| 26:2 | 17.9 | 45.7%（补过头） |

两条关键结论：

1. **【财】几乎不是杠杆**：从 0 加到 40 只把先手胜率从 72.1% 压到 70.0%。
   单局只有 ~11 回合，后手活不到【财】滚起来。**只有【气】能用**。
2. **【气】要加到很大才有效**（+23 = 把后手的气池从 15 抬到 38）。
   这说明先手的结构性优势非常强，而不是轻微偏差。

> ⚠️ 旧版本文档曾写「`4:2` 收益饱和，取 `laterQi: 4`」「先手 75.3%」「【财】给多了反而更糟
> （0:9 → 81.4%）」—— 那些数字是在 **AI 经济完全失灵 + 种子掺入补偿参数** 的双重污染下
> 测出来的，已全部作废。详见第九节 #18。

#### 4.2.1 三选一改「取牌台」后的重测（2026-10-07）

三选一从 `pick_draft()`（点一下取走、**顺手清空牌面**）改成**常驻取牌台**
（`open_draft/do_take_draft/close_draft`，每回合免费 1 张 + 付费上限 3 张）之后，
AI 与玩家的每回合手牌增量都变大了。**重测发现对局被整体拉长约 1 个回合，但胜率结构基本不变**：

| 后手补偿（气:财） | 平均回合 | 中位回合 | 先手胜率 | 局数 |
|---|---|---|---|---|
| 0:0 | 10.7 | 8 | 74.5% | 400 |
| **23:2**（采用） | **18.2** | 15 | **49.8%** | 400 |
| 24:2 | 18.4 | 15 | 49.3% | 400 |
| 25:2 | 18.7 | 16 | 48.3% | 400 |

> ⚠️ **方差警示**：同一档 `23:2` 在 200 局抽样中读到 **54.0%**，在 400 局中读到 **49.8%**。
> 这与 §4.2 表下「±3pp 种子方差」完全一致 —— 所以**任何 <400 局的单点差异都不能当成
> 机制变化来解读**。本项目的平衡结论一律按 **≥400 局** 采集。

| 人数 | 补偿（气:财） | 平均回合 | 偏斜 | 改造前偏斜 |
|---|---|---|---|---|
| 3 人 | **1:2**（采用） | **17.1** | **15.8** | 19.7 |
| 3 人 | 1:0 | 17.8 | 10.4 | — |
| 4 人 | **0:2**（采用） | **18.8** | **21.2** | 22.8 |
| 4 人 | 0:0 | 18.5 | 19.2 | 24.5 |

三条新结论：

1. **回合数整体 +1**：3 人 16.3 → 17.1；4 人 17.7 → 18.8。
   4 人局 **18.8 已略超设计窗口 12~18**，是目前唯一压线指标；2 人局 18.2 同样在边缘。
   根因是取牌台让手牌更快堆起来 → 防守资源更多 → 拖长。
2. **胜率结构未被破坏**：2 人局先手仍旧 ~50%，3 人局偏斜反而**变好**（19.7 → 15.8）。
3. **【财】补偿在多人局里已基本失效**：3 人局 `1:0`（去掉财）偏斜 10.4 **优于** `1:2` 的 15.8；
   4 人局 `0:0` 偏斜 19.2 **优于** `0:2` 的 21.2。两处都指向「财补偿可以去掉」，
   但差异在噪声量级（240 局 ×4 座），本轮保守起见**未改默认值**，留待 ≥600 局专项确认。

> **血泪教训（新增）**：任何改动「手牌/资源增长率」的机制（取牌台、抽牌、免费额度、
> 经济曲线）都**必须重扫平衡**，否则文档里的回合数会静默失真 —— 本轮如果没有重扫，
> 就会带着「17.7 回合、偏斜 22.8」的旧数字继续迭代下一代机制，误差逐轮累积。

#### 4.2.2 技能去同质化后的重测（2026-10-08）

把 `active()` 那张「按 sub 二选一」的表换成 51 条原型池（见 §3.0）之后，
**伤害吞吐的结构变了**：旧版 130 张【神】+【佛】共享的「镇压」可以无视阶数直接
拔掉对方一张【地】卡，87 张【地】共享的「袭人」在高阶还会追加削场 + 弃牌；
新版这两条只是 51 条原型里的两条。结果 **2 人局后手补偿需要重扫**：

| 后手补偿（气:财） | 平均回合 | 中位回合 | 先手胜率 | 局数 |
|---|---|---|---|---|
| 0:0 | 16.0 | 8 | 64.7% | 150 |
| 8:2 | 22.8 | 13 | 53.3% | 150 |
| **10:2（采用）** | **26.2** | **14** | **48.7%** | **300** |
| 11:2 | 26.3 | 14 | 47.0% | 200 |
| 12:2 | 25.6 | 15 | 48.0% | 150 |
| 16:2 | 29.9 | 17 | 44.0% | 150 |
| 20:2 | 32.1 | 21 | 40.7% | 150 |
| 23:2（旧值，已废弃） | 33.3 | 21 | 39.3% | 150 |

结论：

1. **旧值 `23:2` 变成了「补过头」**（39.3%，后手优势）。取 **`10:2`**：200 局 49.5%、
   300 局 48.7%，两次抽样互相印证。注意 `10:2` 恰好是 §4.2 里那个「已废弃」的旧旧值 ——
   它不是被数据否掉的，是被当时那条 AI 经济 bug 否掉的，现在 bug 修了、技能也换了，
   数值又回到了 10。
2. **无补偿时的先手优势反而变小了**（72.1% → 64.7%）：旧版「镇压」对先手是极强的滚雪球
   工具（先手上场 → 立刻拔掉你刚上的地卡），技能摊平之后这个放大器被削弱了。
3. **单局被整体拉长**：0:0 的平均回合 11.1 → 16.0，补偿后 17.3 → 26.2。
   原因同上，伤害与拔除吞吐下降。中位数（8 / 14）说明分布右偏、长尾变厚，
   但仍在 `fatigueStartRound = 30` 的兜底之内（SelfTest §6 实测最长 92 回合）。
4. 多人局（2026-10-08，每组 100 局）：3 人 `1:2` 平均 **19.7** 回合、偏斜 28.0；
   4 人 `0:2` 平均 **25.4** 回合、偏斜 10.0。**两项平均回合都超出了设计窗口 12~18**，
   属于本轮技能改造的已知副作用 —— 见第八节「已知边界」。

### 4.3 集火目标的平手判定

`GameState.opponent_of()` 在【气】相同时**不再按 `players` 数组顺序**取第一个，
而是取「顺时针最近」的一位：

```gdscript
var dist: int = (e.pid - p.pid + n) % n     # 平手时 dist 小的优先
```

原因：所有 AI 都按数组顺序取第一个平手目标时，3/4 人局里 南/西/北 会**全部扑向东**，
死亡顺序完全由座位序号决定 —— 实测「南」的胜率被压到 10%。
改成顺时针后集火关系自然成一个环，每人承受的压力对等。

> **测平衡时注意**：`ai_level` / `ren` / `mingli` 如果是按座位固定分配的，
> 「座位胜率」测出来的其实是**卡组强度**。早期 `RENS[i % 6]` 让「南」永久绑定
> 正一道士（15 气），南的胜率虚高到 68%。现在都随对局种子轮换。
>
> 还有一层更隐蔽的**取模基准耦合**：早期 `ai_level = 1 + ((i + seed) % 3)` 与
> `ren = RENS[(i + seed) % 6]` 共用同一个 `(i + seed)`，于是
> `RENS[0]=凡人`、`RENS[3]=巫女` 永久落在 level 1（EASY），而 EASY 不参与
> 刷新/购买/升级——**偏偏这两个阵营正是靠【财】升级的**。结果整轮扫参里
> 【财】无人消耗，「财补偿无效」的假象就是这么来的。
> 现在改为独立混合 `posmod(i * 2 + int(seed / 7), 3)`。

## 六、卡牌 2.5D / 陀螺仪的实现

`CardView` 把结构分成两层：

```
CardView (Control)          ← 动态投影 + 双重描边 + 选中呼吸光圈，用 _draw() 画
 ├ _face (Control)          ← 这一层整体做旋转 / 缩放 / 位移；clip_contents = true
 │   ├ _art2  (TextureRect) ← 阵营色偏移层 → 随倾角正向位移，制造「厚度」
 │   ├ _art   (TextureRect) ← 主卡面 → 随倾角反向补偿（billboard，始终朝向镜头）
 │   ├ _overlay (Control)   ← 上下暗角 + 金色分隔线 + 闪卡流光 + 冷却黑幕 + CD 转圈
 │   └ 文本层 / 血条
 ├ _glow_layer (Control)    ← ★ 冷却结束的四边外发光，_face 的**兄弟**（不裁剪）
 ├ btn (Button)             ← 透明全屏点击层
 └ _badge_l / _badge_r / _skill_btn   ← 场上模式徽标 + 技能图标
```

> **`_glow_layer` 为什么必须是 `_face` 的兄弟节点？**
> `_face.clip_contents = true`，所有溢出卡面的绘制都会被裁掉。
> 把"四边向外发光"画在 `_overlay` 上，光晕一出门就被切平，
> 退化成贴着卡边的两条暗线 —— 玩家根本看不出"冷却结束了"。
> 又要裁剪（防卡面溢出）又要发光（必须溢出），只能拆成两层。

每帧 `_process` 里用**弹簧阻尼**代替线性插值（带轻微过冲，不生硬）：

```gdscript
var acc := (_tilt_goal - _tilt) * 150.0 - _tilt_vel * 14.0   # 弹簧 + 阻尼
_tilt_vel += acc * delta
_tilt     += _tilt_vel * delta
_face.rotation = -total.x * 0.14                              # 绕 Y 轴"立起"
_art.position  = Vector2(-total.x * 7.0, -total.y * 5.0)      # billboard 反向补偿
_art2.position = Vector2(3.0 + total.x * 5.0, ...)            # 厚度层正向位移
```

**Billboard「始终朝向镜头」**：倾斜时主卡面反向平移（并放大 6% 遮住边缘），
视觉上画面内容始终正对玩家，只有边框和厚度层在动 —— 这是伪 3D 看起来「立体」
而不是「纸片在晃」的关键。投影也会随倾角反向偏移、随悬停放大。

### 手牌悬停抬升（KARDS 手感）与「精确还原」

手牌是**扇形排布**（虚拟圆心在下方），每张卡都有 `home_pos / home_rot / home_z`
三个"原位"字段。悬停时用同一套弹簧驱动 `_lift_t`（0→1）：

```gdscript
position = home_pos + Vector2(0, -58.0 * _lift_t)   # 抬起
rotation = home_rot * maxf(0.0, 1.0 - _lift_t * 1.2) # 摆正（越抬越正）
scale    = Vector2.ONE * (1.0 + 0.13 * _lift_t)      # 放大
z_index  = 200                                       # ★ 盖在其他手牌之上
```

鼠标离开时 `_lift_t → 0`，结束时**显式写回 `home_pos / home_rot / home_z`**。
之所以要"显式写回"而不是"反向算回去"：扇形角度是每张牌独立的，
一旦某次归位差了几个像素，下次悬停就会在错误的位置继续偏移，
**误差会一轮轮累积，扇形最后会散成一堆乱牌**。这是实测踩过的。

> 点击手牌 → `_on_hand_click()` 选中 + 直接打开卡牌详情面板
> （详情里再给一个「起乩上场」金按钮，作为拖拽之外的兜底路径）。

### 拖拽残影：按"层"清理，不按"指针"清理

`BattleScreen._prune_ghost()` 是唯一的清理入口：

```gdscript
func _prune_ghost() -> void:
	if _ghost != null and is_instance_valid(_ghost):
		_ghost.queue_free()
	_ghost = null
	if _drag_layer == null:
		return
	var active := CardView.active_drag          # static var，全局"当前正在拖的那一张"
	if active != null and is_instance_valid(active) and active.dragging:
		return                                   # 有人正在拖 → 一根手指都别碰
	for ch in _drag_layer.get_children():
		ch.queue_free()                          # 否则整个拖拽层扫干净
```

它在 `_refresh()` 和 `_on_card_drag_drop()` 里都会被调；`CardView` 侧还有
`NOTIFICATION_EXIT_TREE` 兜底补发取消投放。三层保险叠加，见第九节 #19。

**陀螺仪**部分：

```gdscript
var acc := Input.get_accelerometer()   # 静态姿态（重力方向）
var g   := Input.get_gyroscope()       # 动态角速度
_gyro = _gyro.lerp(Vector2(gx, gy), delta * 4.0)   # 低通滤波，避免抖动
```

真机（Android / iOS）上倾斜设备，卡片会跟着倾斜；桌面上加速度计读数为 0，
自动退化成纯鼠标视差。顶栏的「陀螺仪」开关可以随时关掉。

**闪卡**：`foil = true` 的卡（2 阶以上、图鉴里 3 阶）会在 `_draw_overlay`
里画**一条横向柔光带**慢速扫过（周期约 3.2s，`_foil_t += delta * 0.7`，峰值 alpha 仅 0.085）。
> 早期版本是「三条斜向光带 + 5 颗漂移十字星光」，玩家反馈"看着眼睛花"，
> 于是**去掉全部斜向扫光与星点粒子，只保留一个方向的闪光**（需求 7）。
> 想让光更"高级"也不要再加方向数：斜向 + 横斜交叉会互相干涉，产生闪烁感。

**内置演出**：`anim_enter`（弹性飞入，手牌/三选一用）、`anim_lunge`（攻击前冲）、
`anim_shake`（受击抖动+红闪）、`anim_flash`（合成/治疗金闪）、`anim_die`（离场淡出）。

## 九、几个容易踩的坑（血泪记录）

1. **`log()` 是 GDScript 内置数学函数**，不能拿来当自己的日志方法名。
   本项目日志方法叫 `log_msg()`。
2. **`CardView.new()` 之后、`add_child()` 之前，节点还没 `_ready()`**，
   所以 `set_card()` / `set_size_px()` 只能把参数暂存到 `_want_size`，
   真正布局发生在 `_ready()`。所有 setter 都带 `if not _built: return`。
3. **`var x := dict["key"]` 会报 "Cannot infer type"**，因为字典取值是 Variant。
   必须写成 `var x: String = ...`。
4. **Control 根节点**：主场景根节点必须是 `Control` 且铺满全屏，
   否则它下面的锚点布局会拿到错误的目标矩形（会多出窗口边框的宽度）。
5. **`get_viewport().get_texture().get_image()` 必须
   `await RenderingServer.frame_post_draw`**，否则截出来是纯色。
6. **`.json` 数据文件必须写进 `export_presets.cfg` 的 `include_filter`**，
   否则导出后的包体里没有 data/ 目录，游戏一启动就空卡池。
7. **缺立绘不会报错，只会显示成一个黑格子。** 「角色」目录里的图叫 `店小二.png`，
   角色名却是「白店小二」，`_find_art()` 严格按名字匹配就拿不到图 —— 而这个格子
   恰好是新手默认角色。现在 `build_cards.py` 有 `ART_ALIAS` 别名表，
   并且在生成末尾**缺图直接 `SystemExit`**；`SelfTest` §1 也会校验。
8. **语法错会让 Godot 一直挂着而不是退出。** 场景脚本解析失败时主循环照转，
   无头跑测试就会「超时且没有任何输出」。看到「超时 + 无输出」先怀疑 Parse Error，
   用 `--headless --editor --quit 2>&1 | grep -iE "error|Parse"` 快速定位。
9. **`--editor --quit` 不会校验所有脚本**（只校验被扫描到的）。
   真正的验证还是要跑 `SelfTest.tscn` / `UITest.tscn`。
10. **`build/` 目录要放 `.gdignore`**，否则 Godot 会把导出产物当项目资源再导入一遍，
    在 `build/web/` 里生成一堆无关的 `.import` 文件。
11. **发布版模板不支持命令行覆盖场景**（`disable_path_overrides`），
    想验证「打包后数据是否完好」，只能临时把 `run/main_scene` 改成测试场景
    导出一次再改回来。
12. **`Dictionary.get(key, 默认值)` 在「键存在但值是 null」时返回 null，不是默认值。**
    道具卡的 `skills.active` 显式写成 `null`，于是
    `d.get("skills", {}).get("active", {})` 拿到的是 `null`，赋值给 `Dictionary`
    类型的变量就报 `Trying to assign value of type 'Nil'`。
    正确写法是先 `if v is Dictionary` 再取。
13. **给 `PanelContainer` 直接设 `PRESET_CENTER` 再往里塞内容，面板会跑到右下角。**
    因为锚点偏移在内容填充**之前**就按当时的（0×0）尺寸锁定了。
    正确做法是套一层铺满全屏的 `CenterContainer`。
14. **测试脚本里 `add_child(control)` 到普通 `Node` 下，Control 不会自动布局。**
    `UITest` 把 `Main`（根 Control，预设 FULL_RECT）挂在普通 Node 下，
    结果整棵树的 `get_global_rect()` 全是 0 尺寸，拖拽的投放判定直接失效。
    测试里必须手动 `main.size = Vector2(1920, 1080)`。
15. **光环类被动的「累加 vs 取最大」决定游戏能不能打完。**
    【神】的「天威压地」原本在 `PlayerState.aura_enemy_di_atk()` 里**累加**，
    而全游戏 102 张【神】卡都带这个被动 —— 满场【神】能把【地】唯一的气伤路径
    扣到 0，实测出现 **678 回合不结束的死局**。改成 `maxi()` 取最大值后正常。
    （同时加了 `rules.json:fatigueStartRound` 力竭保险兜底。）
16. **平衡扫参必须让「所有配置共用同一批随机种子」才可比。**
    早期 `_sweep_seat` 把补偿值混进了种子（`seed = f(qi, wealth, g)`），
    导致每个配置跑的是**不同的对局**，两次测同一个配置能差出 10 个百分点。
    现在种子只跟 `(人数, 局号)` 有关，配置之间是配对比较。
    > 同一个坑在 `_sweep_duel` 里**又犯了一次**（`seed = 70000 + qi*131 + w*977 + g*37`），
    > 直到本轮才修掉。教训：凡是"扫参"，先看一眼种子表达式里有没有扫的那个自变量。
17. **`round()` 做座位补偿插值会在小数值下把中间座位抹成 0。**
    4 人局 `laterQi=1` 时 `round(1 × 1/3) = 0`，于是【南】一点补偿都没有，
    反而成了最弱位（10% 胜率）。改用 `ceil()`。
18. **★ 动作顺序错了不会报错，只会「静默失败」——这是本项目最贵的坑。**
    `AIBrain.plan_turn()` 原本产出 `[draft, refresh, buy, ...]`，看上去完全合理，
    但 `pick_draft()` 会把 `current_draft` 清空，而 `can_refresh()` / `can_buy()`
    都要求牌面存在 → 排在后面的两个动作**每次执行都返回 false**，
    调用方（`BalanceTest._apply` / `BattleScreen._apply_ai_action`）又没有检查返回值。
    症状：**AI 从头到尾一张牌都没买过，却没有任何报错、日志、断言异常**。
    连带后果：
    - 全模拟没有任何人消耗【财】买牌 → 平衡数据整体失真；
    - 2 人局"先手胜率 52.5%"其实是假的，真值是 **72.1%**；
    - `compensationByCount` 的调参全部建立在错误基线上。

    修法：① `plan_turn()` 改成 `升级 → 刷新 → 购买 → 取牌`，三者共用一个【财】余额；
    ② **让每个动作返回 bool**，`_apply` 把它冒泡出来，并用 `SF_DEBUG=1` 逐条打印。
    ③ **本轮的根治版**：`do_take_draft()` 取走一位就**立刻补一张**，牌面不再被清空，
    于是「刷新 / 再取一张」永远有对象可用，这条"顺序铁律"降级为"无需在意的历史约束"。
    > 同一 bug 在 UI 侧的表现，前前后后换过三版：
    > ① `_select_draft()` "点一下即取牌" → 索引被重置为 -1 →「购买」按钮永远禁用；
    > ② 拆成「点选一张」→「取牌 / 购买」两段式（按钮能用了，但反直觉且清空牌面）；
    > ③ **取牌台**：点卡面即取、取完立刻补位、两个按钮整体删除。
    >
    > **可迁移的经验**：规则层函数返回 bool 而调用方丢弃返回值 = 静默失败温床。
    > 凡是"扫参/模拟"类代码，都值得加一层 `ok=true/false` 的打印。
    更根本的解法是直接给「气/财按座位的显式数组」（`compensationByCount.<n>.qi`）。
19. **★ 拖拽残影不能靠"一个变量"清理，要扫整层。**
    `CardView._input()` 的松开分支原本带着
    `not draggable or card == null or not is_visible_in_tree() or not selectable`
    一串前置判断，`if` 不成立就 `return`（连 `pressed` 状态都不复位）。
    拖拽途中任何一次 `_refresh()` 都会重建手牌、`queue_free()` 掉源卡，
    于是**松开鼠标那一下被整段丢弃**，`drag_dropped` 永不上抛，
    `BattleScreen._ghost` 就永久留在 `_drag_layer` 上 —— 玩家看到"卡住了、位置还不对"。
    修法三层：① 松开一律终结拖拽；② `NOTIFICATION_EXIT_TREE` 补发一次取消投放；
    ③ `_prune_ghost()` **扫干净整个 `_drag_layer`**，并用
    `static var CardView.active_drag` 做全局守卫，只在"没有卡在拖拽态"时才动手。
    > 经验：**"当前正在拖的那一个"和"层上所有残留"是两个不同的集合**，
    > 只维护前者的引用必然漏掉后者。清理类逻辑要按"容器"写，不要按"指针"写。
20. **★ `Control.set_size()` 会把尺寸夹到 `get_combined_minimum_size()` 以上。**
    `TextureRect` 在默认的 `EXPAND_KEEP_SIZE` 下，最小尺寸 = **贴图尺寸**。
    于是：
    ```gdscript
    b.texture = back_tex            # cardback_t 是 180×320
    b.size = Vector2(26, 46)        # ← set_size 内部先 clamp 到 180×320，白设
    b.expand_mode = TextureRect.EXPAND_IGNORE_SIZE   # 改晚了，没人会把 size 改回来
    ```
    结果对手牌背变成 180×320，比大本营【人】卡（62×110）大一圈，横着压过整排大本营。
    **正确顺序：`expand_mode` → `stretch_mode` → `custom_minimum_size` → 最后 `size`。**
    > 这个坑靠截图目测绕了很久（坐标系一直在骗人），
    > 最后是 `--dump` 打印出 `size=(180.0, 320.0)` 一行定位。
    > **凡是"设了尺寸却不生效"，先打印实际 `size`，别猜。**
21. **★ 绝不可以在 `_draw()` / `_process()` 里 `SystemFont.new()`。**
    `UITheme.make_font()` 每次调用都新建一个 `SystemFont` 并重新解析系统字体表。
    后果有两个：① 每帧白烧一次系统字体枚举；
    ② **新建的 `SystemFont` 字形表还没加载完就交给 `draw_string()`，中文会画成"豆腐块"**。
    拜神/敬鬼按钮底部那两团灰方块就是这么来的。
    > 特别容易误判：`Theme.default_font` 是启动时建一次、有充足时间加载，
    > 所以 Label 上的中文一直正常，**只有 `_draw()` 里现建的字体是坏的**，
    > 看上去很像"缺字库"。修法是 `UITheme.font()` 进程内缓存。
22. **`WorshipCard` 的"等比铺满"不能让贴图溢出自身矩形。**
    卡片 82×135、贴图 180×320，按 `cover` 算出来的绘制高度是 145.8 ——
    多出的 5px 会糊到按钮上下两侧，变成**两条白杠**。
    不要靠 `clip_contents = true` 兜底：那会连带把"冷却结束四边向外发光"一起裁掉。
    正确做法是 `draw_texture_rect_region()` —— 把溢出部分**从源图上裁掉**，
    目标矩形就是卡片本身。
19. **★ 生成物被手工改过 = 下一次生成时静默丢失。**
    `data/rules.json` / `data/cards.json` / `characters.json` / `ren_cards.json` /
    `mingli.json` **全部是 `tools/build_cards.py` 的输出**。上一轮为了加
    `boardCap` / `boardUnique` 直接改了 `data/rules.json`，本轮一跑生成器就整个被覆盖，
    规则层 `CardDB.rules.get("boardCap", {})` 读到空字典 ——
    症状是「同名牌能重复上场、场位没有上限」，而且不报任何错（因为空字典是"合法"的默认值）。
    **任何规则常量的唯一真源都在脚本的 `RULES` 字典里**；`data/*.json` 只读不写。
    （`SelfTest §12` 现在有一句 `规则已定义 boardCap` 专门盯这个。）

20. **生成器里绝对不能用 Python 内置 `hash()` 做取样键。**
    字符串哈希每个进程都会掺随机盐（`PYTHONHASHSEED`），`hash("tian_佛_000") % 42`
    每次运行结果都不同 → 卡牌数据每生成一次就变一次，**无法复现、无法 diff、无法回归**。
    统一改用 `zlib.crc32(...) & 0x7FFFFFFF`（见 `_h32()`）。
    > 判据很简单：如果生成器跑两遍产出的文件不一样，那它就不是生成器，是随机数。

21. **★ 「按 sub 分派技能」是同质化的根，不是"模板太少"。**
    旧版 `active(sub, tier, name)` 里只有两个分支：
    `if sub in ("佛","神")` → 镇压；`if sub in ("妖","鬼","魔","奇兽")` → 袭人。
    102 张【神】+30 张【佛】全都走第一条，87 张【地】全走第二条 ——
    于是 **227 张卡只有 6 个主动技能名**（镇压 ×130、袭人 ×85）。
    这个设计看起来"有了 7 种阵营差异"，实际是把同质化从"所有卡一样"换成了"同阵营一样"。
    只要取样键里出现 sub（阵营 / 稀有度 / 分组等**大批量共享**的属性），
    无论池子多大都会被它切成几块。**正确的取样键必须是卡牌自己的唯一 id。**
    `tools/build_cards.py` 现在会在生成末尾打印 `[variety]` 量化这一指标，
    并把「四元组互异数」当作断言级别的护栏 —— 同质化一旦回潮，
    在生成阶段就能看见，而不是等玩家截图来问"怎么所有人技能都是镇压"。

22. **主动技能的「高阶追加效果」必须标 `fixed`，否则和 `per_tier` 双重放大。**
    设计文档要求「阶数越高附带效果越多」，所以 `_active_skill()` 会在 2/3 阶追加一段。
    但追加进来的效果如果也带 `value`，`_apply_tier_scaling()` 会顺手补 `per_tier` ——
    3 阶卡于是同时拿到「多一段效果」+「每段数值翻倍」两个乘数。
    追加效果一律写 `"fixed": True`，`_apply_tier_scaling()` 见到就跳过。
    > 另一个同源坑：追加效果要**刻意避开自家基础效果的类型**。第一版把「守」
    > 的追加写成 `shield_qi`，于是基础就是 `shield_qi` 的「金钟罩」在 2 阶变成
    > 「获得 3 点护盾，获得 2 点护盾」—— 卡面读起来像复读机。
    > 现在五个 school（攻/守/控/术/财）的追加都换到了**不同维度**上。

23. **`summon_to_hand` 的 `group` 和 `random_from_special()` 的寻址方式对不上会静默失灵。**
    `random_from_special()` 内部拼的是 `"天/" + group`，所以 `group` 只能是
    `"四相"` / `"十二生肖"` 这类**特殊卡池**名。而「拜神」「敬鬼」写的是
    `group: "神"` / `"鬼"`，拼出来是「天/神」「天/鬼」—— 这两个分组根本不存在，
    技能一声不响地什么都没抽到（只在日志留一句「召唤失败：卡池为空」）。
    现在 `summon_to_hand` 支持 `subs` 参数（走 `CardDB.random_card_by_sub`），
    按 sub 抽取才对得上「请天 / 请地」的语义。
    > 通用教训：`EffectRunner` 里所有"按名字去卡池找"的效果都应该在找不到时
    > **至少让日志有存在感**，否则玩家看到的是"这张卡用了没反应"。
